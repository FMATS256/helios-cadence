# Architecture decisions
- Subscription automatic and staff-triggered recurring billing share a row-locked database function and unique subscription-period invoice key; daily SQL scheduling generates invoices without approving payments or claiming email delivery.
- Client receipt views reuse authenticated portal payment/profile data, and service visibility derives from one shared active-state filter; presentation never creates receipts or changes Finance approval.
- Portal service identities and subscriptions reuse one invoice-style presentation card; mobile navigation uses an accessible dropdown over the page while desktop navigation stays inline, keeping service actions and account reads unchanged.
- The /account-manager hub and leads workspace reuse existing CRM records, owner-scoped account portfolios and technician dispatch with server-checked portfolio ownership; Customer 360 and NOC share account-access controls, with server-authorized client-only recovery emails and administrator-only ownership linking, to avoid duplicate workflows and staff credential exposure.
- Invoice downloads use the actual Quote Studio PDF with narrowly replaced text operators for saved amounts and allocation-derived labels, so the external design stays intact without changing billing or approving payments. Invoices carry no VAT (rows/column blanked), show the account manager as Sales Rep with their initials as Sales Code, and are emailed from the account manager's address with their signature and the PDF attached via the attachment-capable sender.
- Invoice line SKUs and optional service periods are persisted; catalogue codes are preferred and unmatched legacy/automated lines receive explicit internal identifiers. Saved-line totals and received-payment allocation changes synchronize invoice totals/status in database triggers; documents distinguish invoice balance from customer receivables and never infer a subscription period from its due date.
- The client account portal resolves ownership from administrator-linked profiles, uses authenticated RLS reads and atomic pending payment submissions, and never exposes the staff shell or permits client approval; profile ownership changes are protected by a database trigger.
- Portal invoice payment eligibility subtracts successful gateway receipts not yet allocated from ledger balances, shared by display and payment preflight; Finance approval and official invoice balances remain unchanged.
- Website account opening uses the existing IMT HMAC connection and a service-only atomic database function with durable application IDs; manager selection and contact creation commit together, so retries cannot duplicate accounts or leave partial onboarding.
- Email and original account-opening API addresses share one server handler; a customer-insert trigger saves the assigned manager's in-app alert atomically for every creation path without duplicate alerts on application replays.
- Staff creation, lead conversion and website opening await one shared welcome sender with an atomic customer claim; the existing IMT inbox transport persists personalized signed messages before sending, and failed/ambiguous attempts are never blindly resent.
- Quotation previews and PDF downloads share a saved-value document model; pure PDF generation renders the branded layout without changing external-engine lifecycle or financial calculations.

- Direct Finance payment recording must require a destination cash account and post both its cash movement and balanced journal entry, so recorded receipts always update account and ledger balances.
- Inbox outbound mail uses only the IMT website gateway and saves its message and quotation snapshot before delivery, so failures never cause unrecorded or fallback sends.
- Base44 webhook resolves client ownership from the protected system setting, not incoming customer identifiers, so requester data cannot route tickets to another client.
- Email HTML renders sandboxed/sanitized; attachments require visible message ownership and are copied into retained storage from gateway content or short-lived HTTPS links, never another mail provider. Prepare blobs before clicks; preview only safe image/PDF/text.
- Department senders are authorized from protected staff roles; personal drafts and organization are atomically persisted under owner-only policies, while internal notes inherit enquiry visibility.
- Inbox and transactional signatures share one email-safe table template and staff-title resolver (mobile-safe typography, one linked promo image); custom personal signatures override it.
- Inbox conversation rendering uses a dedicated collapsible message view with the latest message expanded first, authorized thread prefetching and foreground refresh, so older HTML signatures do not delay access to new replies.
- Compose restoration and outbound conversation display remove identifiable staff signature blocks without changing stored messages; delivery appends signatures separately so clients still receive them.
 - Reply composers show the latest inbound HTML in a separate sanitized read-only preview, never inside the editable or outgoing body, so client branding is visible without being sent back.- Client portal sign-in resolves email, username or account number to the login email inside a public server function and returns only a session, so identifiers never expose emails; new accounts get a client-only login (staff roles stripped) whose temporary credentials go in the account manager's welcome email, never overwriting an existing login. Portal banners are administrator-managed rows shown in a top strip.
- Login email and business email are separate: profiles.work_email (when set) is used for sending, mailbox, signatures and manager contact; login email is only for sign-in.
- Technical workspaces are two tabbed hubs (/noc, /techops/dashboard); merged pages live as sections in src/components/techops and collapse their frame via EmbeddedPageContext, while their old URLs remain redirects.
- The Finance AI agent (/finance-agent) reads billing correspondence through the existing IMT gateway and writes proposals; Finance/master-admin approval sends fixed-department reminders or submits email claims for separate payment verification, never treating email evidence as received ledger funds.
- Monthly finance statements use deterministic, secret-authorized scheduling and a unique customer-month delivery reservation; reuse the approved IMT statement hierarchy and official Quote Studio invoice PDFs, retain attachments in Inbox, never create extra invoices or blindly resend ambiguous deliveries, and separate statement currencies and verified received funds.
- Portal statements resolve account ownership from the authenticated profile, derive current and monthly cutoffs without email delivery dependencies, and prepare per-currency PDFs before download clicks to retain mobile user activation.
- The Personal Assistant (/assistant) is per-user and read-only: tools use the caller's RLS client and owner-only tables, so it sees only that user's data and never sends mail or changes records.
- Personal Assistant actions (client emails, follow-ups, draft quotations) are proposals executed only after owner approval in-app or via a tokenised emailed confirm page (GET shows, POST runs); client mail sends from the configured client mailbox, owner reports from the assistant mailbox, one daily report per user-day.
- Emails to the assistant mailbox from a master-admin owner's saved address are answered via the read-only assistant (system-wide lookup tool) and replied only to the owner's stored address, claimed once per provider id; they are not filed as enquiries.
- Firewall changes: Vultr API only, staff-only, logged; sensitive ports/wide ranges never open to everyone.
- Per-order-billed provider orders and server rebuild/restore/app-install requests run only after an ops manager/master admin (not the requester, unless master) atomically claims them; power/snapshots are immediate staff actions.
- Scheduled hooks under /api/public/hooks require Bearer AGENT_WEBHOOK_SECRET; cron calls public.invoke_internal_hook to block outside triggering.
